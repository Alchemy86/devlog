TerminalGB Portal

Sign in, add a friend by code, trade one Generation 1 Pokémon. That is v1, whole. The trick that makes it simple is a fact about the hardware: a Game Boy link trade does not need two Game Boys. It needs one Game Boy and something that answers the cable correctly — and the emulator already ships that. So the portal is not a matchmaking service. It is a Pokémon source, served over HTTPS.

Nobody waits, because nothing is synchronised

The obvious design for "trade a Pokémon over the internet" is a live session: both players online at once, both cables bridged through a relay, real-time. That is a matchmaking and presence problem wearing a trading problem's clothes, and it is why this kind of thing usually does not get built.

The observation that dissolves it: the cartridge does not know or care what is on the other end of the cable. It knows the link protocol. The emulator already ships a virtual link partner that speaks it, fed by a source of Pokémon. So make the portal that source.

A trade becomes a handful of ordinary HTTP requests. Both players trade against their own local partner, in their own time. One deposits a description; the other collects it whenever they next sit down. There is no session, no lobby, no presence, and nobody waits for anybody.

What is deliberately not in v1, and the UI says so

Live link sessions and battles. The browser as a primary client. Strangers, a public lobby, matchmaking. Multi-Pokémon trades. Presence beyond a friends-only "terminal connected" badge. Generation 2 and 3. Mobile.

The list is written into the product rather than into a roadmap document, which is the difference between a scoped v1 and a v1 that is quietly missing things.

Session-held sprites are a licence boundary, not a cache policy

The collection browser shows a friend's party and boxes — what their own terminal reported — including the sprites. Those sprites came out of the owner's own emulator running the owner's own cartridge, and they are held for the session only. When the terminal disconnects they are purged. The portal keeps no sprite store of its own, has no server-side fallback, and never reuses one user's picture for another user's Pokémon of the same species.

A disconnected user shows no sprite at all, and that is the correct behaviour rather than a degraded one. The same reasoning shapes the offer card's picture: it is artwork its owner's emulator sent with this offer, held for that offer's life, shown only to the friends it is addressed to. Three separate paths null it out — cancelling the offer, the auto-withdraw, and an update that changes the species. That last one is the interesting case: the Pokémon evolved, so the stored picture is now of the wrong creature, and a wrong picture is worse than none.

The purge has a subtlety in it that is worth knowing about generally, and the rate limiter has the same one — see below. The lapsed-sprite purge runs as a separate UPDATE before the SELECT that reads the collection, and must not be merged into one statement, because a data-modifying common table expression is invisible to the same statement's SELECT under Postgres's snapshot rules.

Four bugs whose cause is one line

The repository keeps a "sharp edges" list where every entry cost real time or was caught in review. These four are the ones that generalise past this codebase.

"The Pokémon images don't work"

The emulator was sending an offer card — sprite, types, determinant total, a shiny prediction — right alongside the Pokémon spec. The offer endpoint read only the spec and the save identity beside it. The card object was arriving on every request and being dropped on the floor, so every offer showed the no-picture placeholder.

The fix came with two rules that are more interesting than the bug. First: the card's sprite is a base64 PNG, not the collection's raw pixel array, so it is decoded on the way in — indexed or RGB8, non-interlaced — into the portal's one sprite shape, and the PNG's own header is the authority on geometry. A declared width that disagrees is a refusal, and decompression runs with an exact output limit so a compression bomb cannot spend memory. Second: a malformed card is dropped field by field, never a 400. An optional decoration from the other side of a shared contract must not turn a valid offer into an error — but the reasons ride back on the reply, precisely because the silent version of that is the bug above.

Every poll looked too fast

The device-code login flow enforces a minimum polling interval, and the endpoint has to both read the last poll time and stamp a new one. Written the obvious way — one UPDATE … RETURNING — it silently never works, because RETURNING sees post-update values. The endpoint reads its own new timestamp, computes an interval of zero, and interval enforcement quietly does nothing.

The shape that works reads the previous value under a row lock first and updates in a second CTE. It was caught before commit by reading the Postgres documentation rather than by a test — and there is now a test, so a "tidy-up" back to a single statement turns red.

A row id that was a string

pg returns 64-bit integers as JavaScript strings, by default, because they do not fit safely in a double. Every id in this schema is a bigint, so Number.isInteger(id) guards silently stopped guarding and ids in JSON quietly became strings. Measured: a friendship id came back as "1". One type-parser registration at the database module fixes it globally.

A grid that could not shrink

The Pokémon cards live in a CSS grid. Written as repeat(auto-fill, minmax(16rem, 1fr)), that grid physically cannot get narrower than 16rem — so below about 350 pixels it made the whole document wider than the viewport and every panel on the page got clipped mid-word at the right edge. The min(100%, 16rem) spelling is load-bearing, not stylistic.

The same class of fault lived in two other places: the site header, where the brand plus the navigation come to about 350 pixels with no wrapping allowed; and a form label inside a card, where a flex item's automatic minimum size is its content width, so a 16rem minimum on one label spilled the card at every width. Gen 1 has no shiny Pokémon, and every surface says so

Generation 1 has no shiny Pokémon and no Hidden Power. What it has is determinant values, from which Generation 2 derives both. So every surface in this product reads "would be shiny if traded to Gen 2" and "Hidden Power if traded to Gen 2" — never "is shiny".

That phrasing is not negotiable, and it has a layout consequence that was accepted rather than shortened away: the Hidden Power line is the one line in a card allowed to wrap to two, because the full phrase does not fit one card-width line. Wrapping varies a card's height, never its width, so the narrow-width guarantee above is untouched.

The portal recomputes the prediction from the determinant values itself, against the published Generation 2 shininess rule, and verified it against the emulator's own test vectors. It never trusts the flag on the wire, which is the right default for any field one side can compute and the other side sends.

And an honest limit on what a portal can verify

Every incoming Pokémon spec is validated against Generation 1 tables — species, moves, level, determinant values, name character sets — at deposit, and re-resolved by the receiving client against its own cartridge's tables, which is the real boundary. But Generation 1 has no anti-cheat, and the portal does not pretend to verify legitimacy. The trade log says "done" because each side attested it, and it says so in those terms.

"Same Pokémon" is likewise a stated heuristic rather than an identity: original trainer id, original trainer name, determinant values and nickname, where both-default nicknames across an evolution-line species change still match, because the game renames a never-nicknamed Pokémon when it evolves. Species is deliberately not in the key, because evolution changes it. Every ambiguity withdraws the offer rather than guessing — and a rename simply breaks the match, which fails safe.

The relay that exists, works, and is not deployed

There is a live-link relay in the repository: a Cloudflare Durable Object, 118 lines. It is for the future features — real-time link battles, possibly side-by-side game streams. It is not deployed anywhere and nothing in the shipping app uses it. The README says, in as many words, that if you are reading this to debug production you should stop.

Why a Durable Object rather than the platform everything else runs on? Because Vercel's own WebSocket documentation says "new WebSocket connections are not guaranteed to reach the same Vercel Function instance" — and a live link session is two specific people, which is to say two connections that must meet in one place. A Durable Object is addressed by name, so both players who name the same session id land in the same object by construction. That is the entire reason for the choice.

The relay is deliberately dumb: it pairs at most two seats per session, relays opaque frames of at most 64 bytes without ever parsing a link byte, reports a byte sent with no far end rather than silently dropping it, and announces a departing peer to the survivor. Six checks assert exactly those properties, including that a 644-byte Generation 1 party block relays in order. Last verified green, twice, on 14 Aug 2026.

And what it still needs before production is written down rather than assumed away: token validation on the upgrade request, an idle timeout for abandoned sessions, and peer-fault propagation so one side's fault poisons the other's write instead of leaving a half-trade.

Security posture, stated as what it is

  • Sessions belong to the authentication provider; nothing is hand-rolled. The only tokens this repository mints are the CLI's opaque bearer tokens — 256 bits of randomness, stored only as a SHA-256 hash, 30-day access and 90-day refresh, with rotation and reuse-detection revocation.
  • Device codes expire in ten minutes, are single-use, and enforce their polling interval with per-IP and per-user rate limits. Approval requires a signed-in browser session, never a bearer token.
  • Friend codes are cryptographically random from a 30-symbol alphabet, and the lookup endpoint is rate-limited and returns one generic error for every failure mode, so codes cannot be enumerated.
  • No saves, no ROMs, ever. There is no upload path. The entire per-trade dataset is the two ~250-byte specs and their timestamps.

The rate limiter carries the same Postgres subtlety as the sprite purge, and the behaviour it produces is documented rather than surprising: a data-modifying CTE is invisible to the same statement's SELECT, so the limiter counts only prior attempts. "Max" therefore means "allow exactly max, deny the max-plus-first" — and an end-to-end check pins that eleventh attempt returning 429 so the meaning cannot drift.
