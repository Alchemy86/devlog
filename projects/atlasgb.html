AtlasGB

Memory maps for Game Boy cartridges that carry the evidence for every claim they make. Maps for these games already exist — the disassemblies have their wram.asm, the wikis have tables, the cheat sites have lists. They are transcriptions: somebody read an address once and everybody since has copied it. AtlasGB differs in exactly one way, and it is the whole point.

One atlas is published: Pokémon Red and Blue, English (USA/Europe). Work RAM and high RAM are 100 % accounted for with no holes. Red and Blue build from one source and share their work RAM map, so one atlas covers both.

The problem is not that they are wrong

A transcribed memory map is not so much wrong as unauditable. You cannot ask it how do you know? — so a typo made in 2004 is still there, indistinguishable from the two thousand correct rows around it. There is no way, from inside any of them, to tell a right address from a plausible one.

Every claim carries its evidence — and the entries with no evidence at all say so, rather than borrowing confidence from the rows beside them.

AtlasGB, the whole premise

That is possible because the evidence is produced by a cycle-accurate emulator — TerminalGB — that runs the cartridge and watches what it does. The atlas is a published dataset, not an application: one tab-separated file per cartridge is the source of truth, and every page, index, table and JSON file in the repository is generated from it.

Four tiers, and each one's limit is stated rather than glossed

R — the cartridge names it

The address appears in the ROM image as the operand of an instruction that takes one. ld [nn],a is EA lo hi; ldh [n],a is E0 n.

This is a byte scan, not a disassembly, and the limit follows from that immediately: two bytes of graphics data preceded by a byte that happens to be $EA look exactly like ld [nn],a, so a single hit is weak — the scan records the count, which for a real address is typically dozens. What it cannot do is produce a false negative: an address the game really does load will be found.

L — observed live

The byte changed while the cartridge ran a fixed button script on a cycle-accurate emulator, from a cold boot with no save. Emulation is deterministic, so the same cartridge and the same script give the same answer to anybody holding them; that is what makes it a baseline rather than an anecdote.

The script plays the opening and then walks and opens menus, so it never reaches a battle or a storage box. An entry it does not mark is honestly unmarked: not observed, never not used. Extending that script is the single highest-value contribution anybody could make to the repository.

I — an invariant covers it

A named, hand-written check proved the entry means what it says, not merely that it exists. These are the strongest rows in the file and the only kind that can catch an address which is real, live, and describing the wrong thing.

They are not clever, and that is deliberate. Every nybble of the money field must be 0–9, because it is packed decimal and a wrong address almost certainly would not be. The party arrays must agree three ways — the count, the flat species list, and the species inside each 44-byte structure — because those are three statements of one fact, written at different moments. Two files in the consuming emulator disagreed about the battle structure's size, 28 in one and 29 in the other; the map settles it, and the fact that the trainer-class field follows immediately is the proof.

The strongest is the asymmetric one: every species you carry, converted from its internal index through the Pokédex-order table read out of the cartridge, must have its bit set in the owned bitfield. Three independently located things have to agree. Shifting that table by one byte breaks it — and breaks the separate content check beside it — which was measured rather than asserted.

The best row in the file is the one that admits it proves nothing

There is an obvious invariant for the Pokédex: owned ⊆ seen. You cannot own a Pokémon you have never seen, so every bit of the owned bitfield must be set in the seen bitfield. It is cheap, it is true, and it looks like it pins both addresses.

It does not. The relation is symmetric when the two sets are equal — so on a save where everything seen was also caught, swapping the two symbols survives the check. It passes, cheerfully, on an atlas that has the two addresses the wrong way round.

The check says so when that is the case, rather than reporting a pass it has not earned. It is written up on the verification page as a worked example of exactly this failure mode, and the sentence it exists to hold up is worth the whole section:

A check that quietly passes for the wrong reason is worse than no check.

docs/verification.md

The same page reports the harness catching one of its own author's errors while it was being written: the signature used to confirm the species-name table started at RHYDON had D as $84 instead of $83. An invariant is only as strong as the save it runs against and the constants it was built from, and both of those are stated.

TACKLE is 95 per cent and we said 94

This project's most useful entries are the corrections of its own beliefs, and this is the cleanest of them, because nothing failed.

A section literally headed "two things the cartridge settled" recorded that TACKLE's accuracy byte is 240, not 242 — 94 %, where the community usually quotes 95 %. The claim had propagated into a policy document, into a Rust module's doc comments and into a project memory file, and sat there for as long as those files existed. No run was affected. It was found by re-reading the move table while writing a page about discoveries, on the grounds that a page about discoveries which repeats a number without checking it is not worth having.

The method is the part to copy: read the table straight out of the cartridge, six bytes per move, and check the reading against moves whose values are not in dispute before believing anything about the one that is.

Every row but the one under investigation matches the values Generation 1 is known for, which is what says the table is being read at the right offset with the right stride.

And the origin of the wrong number is instructive: 94 % of 255 is 239.7, which rounds to 240 — the byte you get by computing it from a percentage you already believed, rather than reading it. The code was never wrong. Only the prose was.

Accuracy is not the number in the move table

A related finding, and a much better argument for large sample sizes than any statistics lecture. The hit calculation scales a move's accuracy byte by the attacker's accuracy stage and by the inverse of the defender's evasion stage — so a policy reading the ROM value is reading a number that has not been true since the first SAND-ATTACK landed.

A Pidgey's SAND-ATTACK takes a 95 % TACKLE to 62 % and then 47 %. Both ratios come out of a stage-modifier table read from the cartridge, located by searching for its own opening bytes — a signature that occurs exactly once — and re-checked on every read against two properties: the first pair must be 0.25, and the middle pair must be exactly 1:1, because a table read from the wrong place almost never has a neutral stage in its middle.

The reason this is on the page at all is how it surfaced. Three of 3,000 attempts at one scenario died in the same shape: at 2 HP against a Pokémon on 1 HP, the driver chose to swing rather than escape, because a good roll would end it first — a coin flip taken in place of an escape that would also have removed the incoming hit.

Found only at N = 3,000

Two separate 600-attempt runs were clean. The bug was not rare in the mechanic, it was rare in the route — it needs a Pidgey that has had time to use SAND-ATTACK twice. That is a certification bar earning its keep rather than being a formality.

There is a second trap sitting underneath it that the atlas carries its own warning about: in the stat-stage block, 7 is neutral, not 0, and the block is zeroed work RAM until the battle-init routine writes the sevens. A sample taken on the first frames of a battle reads 0 everywhere and looks like every stat six stages down.

The map, measured rather than recalled

Not every finding is about memory. Some of them are about the shape of the world, and the ones that matter are the ones where the intuitive model is wrong.

One scenario lost 17 of 600 attempts, every one of them on the same row of Viridian City, sliding between x=26 and x=32, with the leg's first waypoint at (29,26) unreachable above it. The first model of the trap was topological and it was wrong: a flood fill says (29,26) is fine — there is a 13-step path back to it crossing no warp tile — and reports nothing.

Two things had to be modelled exactly before any check could catch it. The ledge: stepping down off row 26 does not land on row 27, it jumps to row 28, and the one-wayness is in the cartridge's own data — eight ledge entries, for facing down, left and right, and none for up. The walker: a greedy waypoint walker is not a path-finder, and below a one-way ledge it slides along the wall, which is precisely what the 17 failing runs did.

The repair is not a bigger budget. The row the mart door opens onto crosses the city cleanly, sits six rows above the ledge, and the rest of the chain finishes even from below the ledge — so the leg turns west first and an overshoot costs nothing. This shape has now appeared three times, which is what makes it a rule rather than three anecdotes:

A waypoint whose overshoot is unrecoverable is a waypoint pointing at a trap.

Prefer the turning point with slack around it

The tool that makes that rule checkable is honest about its own limits, which is the reason it is worth having: it is a design aid rather than a gate. It cannot know whether an overshoot is reachable — that needs the map's people, and a person in the way is what pushed the walker over the ledge in the first place — and it has no model of the driver's stuck-sidestep, so it over-reports.

Sixty entries carry no evidence, and the sixty are pulled apart

Counting every entry rather than only storage, 60 carry no verify token at all. That number is worth taking apart, because most of it is not a gap in the running of the checks; it is a gap in what the checks are built to look at.

WhatCountWhy it has nothing
ROM routines and data tables 53 The operand scan is deliberately scoped to RAM addresses — it asks "does the game load this address as data", which is the right question for a byte of storage and the wrong one for a routine's entry point. The live sweep cannot apply either: a ROM byte never changes. Three of the 53 are checked, by a fourth method — a byte-signature content check. The other 50 have no method wired up, and the honest fact is that the mechanism already exists and generalises; nobody has pointed it at them.
Storage bytes the fixed script never touches 3 Real work-RAM addresses that need a battle, a full sprite roster or a storage box — none of which the opening-and-overworld script reaches. Extending the script closes these, not a new method.
Cartridge-RAM free markers 4 These rows assert "this byte is unallocated", to keep the completeness invariant honest. That is not a claim a cartridge run can confirm or deny — there is nothing to check.

So roughly 50 are "a method exists and nobody has pointed it here yet", 3 are "the standing method has not reached this byte yet", and 4 are not really unverified claims at all. None of the 60 needed a new kind of check to be invented — which is a far more useful statement than "98 % evidenced".

Separately, seven storage entries carry no evidence and are listed by name in the evidence record. They stay marked as unevidenced, and the validator prints them by name on every run so they cannot quietly disappear. That honesty is the product.

The evidence column is not editable by hand

Evidence tiers are produced elsewhere — proving an address against a running cartridge needs an emulator — and arrive as a report. The evidence record stores the run's provenance and a SHA-256 digest of the verify column it produced, and CI checks it. Two consequences, both intended:

  • editing a tier by hand turns CI red;
  • adding a symbol to the atlas without re-running the verification turns CI red, because the new symbol changes the digest — the atlas grew, so the last run no longer covers it.

The digest is over symbol → verify only, so writing a description or rewording a chapter does not invalidate a run.

On 25 August 2026 the tiers were re-produced from scratch against a second, independent boot of the same retail cartridge and save, run twice for determinism. Both runs produced byte-identical results and both agreed with the previously published run: zero entries moved tier. That is itself the finding — the atlas's 2,898 claims disagree with the cartridge in zero places — and it is logged whether it finds something or not, because a verification pass that found nothing wrong is worth recording as of when it ran.

Two different kinds of being wrong, two different homes

The discoveries page is where the cartridge surprising us goes. A separate data-issues page is where this atlas being wrong goes. The distinction is not cosmetic: conflating them would mean a reader cannot tell "the game does something strange" from "we published something wrong and fixed it", and those carry opposite implications for whether the rest of the atlas can be trusted.

A symbol name is not a source

The description column says what an address is for, and it is written from a source: what the disassembly says the symbol is, what the emulator measured on the retail cartridge, or a structure this atlas already documents. A symbol name on its own is not a source — the atlas already shows the symbol name, and a plausible sentence derived from it is exactly the thing this project exists as a reaction to.

That is why ninety map-script bytes are blank and one is not: only Oak's laboratory has been driven and watched.

When the well of already-written-down evidence ran dry, the next place to look was not the symbol name — it was the cartridge. A standalone tool steps a real playthrough and records, per address, which code writes it, when, and to what values. Grouping addresses by their writing routine is what actually produced measured linkage: a sound-engine channel-init routine writing nine per-channel fields together; two shadow sprite slots never touched independently regardless of which routine does the touching; a stat-stage reset routine distinct from the one an existing description already credited.

A ROM entry's length column is "distance to the next atlas entry in the same bank" — exhaustively accurate for RAM, wildly inflated for a sparsely covered ROM bank. The species-name table's recorded length is 13,598 bytes because nothing else in its bank is named yet. An unguarded range match credited it with writing dozens of unrelated bytes before a small-window cap caught it.
The fixed low bank is always mapped, whatever the bank register says. Grouping its writers by (bank, PC) instead of by PC alone splits one shared routine into several apparently different ones, by the accident of whatever bank happened to be switched in. A 39-address generic byte-copy utility at $00B6 was nearly credited as evidence for a dozen unrelated relationships.
The script's own state-forcing writes can be misattributed to whatever instruction happens to run first in the next traced frame — the detection is a diff against a shadow map taken once at the start of the run, so the forced write's "before" value is already stale. It can look like the game's own code wrote two addresses in one instruction when really the tool wrote them itself, outside any frame. Any directly forced address must be excluded from the analysis entirely, not merely have its first event distrusted.
A one-off investigation binary must load a real save, or its negative findings about game mechanics are not trustworthy. Two tools written passing no save started a brand-new game each run, and a forced trainer battle never progressed past its first menu whatever the input. Loading the real save and re-running the identical code produced a complete battle — damage both directions, a second party member sent out, ending in a genuine black-out. A negative result from a fresh game is a finding about fresh games.

The rule that came out of the linkage work is the sharpest sentence in the repository: a shared writer is measured, but "measured" and "examined" are not the same thing. The first backfill populated only six of thirty-one measured writer-groups, because those were the six the prose actually stood behind. Three were explicitly declined — one of them named in the prose as "plausibly one generic copy-N-bytes utility reused across three unrelated features".

Two held-back groups were examined the next round rather than left open indefinitely, by a bounded check that needs no emulator and no disassembler: read the raw ROM bytes at the writer's program counter and see whether the shape is a tight, counted, value-agnostic loop (generic) or a routine whose instructions reference the specific fields it writes (purpose-built). Both turned out generic — a constant-fill loop, and a stack-pop-based bulk transfer that points the stack pointer at a source buffer as a speed trick. The suspicion was confirmed rather than resolved the other way, which is the outcome worth publishing.

Two things about the licence, stated plainly because they are easy to overstate

The atlas content is CC BY-SA 4.0; the tooling and the schema are MIT, and the boundary is a path rather than a judgement call. The split is not cosmetic: somebody producing a compatible atlas elsewhere is worth more than an exclusive one here, and a schema you need permission to implement is a schema nobody implements. Share-alike exists so that nobody can absorb a verified atlas into a closed product and quietly strip the evidence off it.

The addresses are still facts and nobody owns them. Anyone can re-derive every one from the public disassembly. Share-alike reaches the compilation, the evidence and the prose — not the number $D163. And MIT already granted cannot be revoked: every copy published before the relicence stays MIT. It is a re-pin that brings share-alike in, not the passage of time.

One trade-off is taken deliberately and written down rather than tidied away: the licence file opens with the path table rather than with the bare MIT text, so GitHub's licence detector will likely show "Other" in the sidebar instead of "MIT". That is the honest outcome — a sidebar reading "MIT" over a repository whose data is share-alike is worse than one reading nothing.

The addresses, symbol names and structure layouts are facts about the cartridge, derived from a built pret/pokered checkout. The names in particular are the disassembly projects' work, built up over many years by many people, and they are the most useful thing in these files. They were not invented here and are not claimed here; the disassembly's prose and comments are not ours to copy, so every description is written from scratch.

Where these numbers come from

The claim count, the tier counts and the chart above are read from atlases/pokemon-rb/data/atlas.tsv, the atlas's own source of truth, and cross- checked against the repository's committed data/evidence.json. That record names the emulator commit that produced the run, the cartridge by title, region and SHA-1, the script that was played, and the run date (25 Aug 2026).

The cartridge measurements — the move table, the stage-modifier ratios, the Viridian City walkability grid — were read off a retail Pokémon Blue cartridge with the project's own tools and, for the ledge-trap block, with no emulator run at all. No ROM is distributed; the reproduction commands point at your own.
