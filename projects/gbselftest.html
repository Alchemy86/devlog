GBSelfTest

A single-file Game Boy test cartridge. Boot it on any emulator or a real console and it tells you what is broken and where to read about it — no host, no reference images, no setup. It runs 102 checks unattended in under ten seconds and reports the verdict twice over: as text on the screen, and as the same text out of the link port, so a machine can read it with nobody watching.

What it is

Most test suites tell you a number. GBSelfTest tells you which behaviour is missing, in hardware terms an author can act on, and where the write-up is. Every check prints a stable code with its failure; the link port carries the whole story, including the measured value, one line of hardware explanation, and the URL to read. For CI, an existing runner captures the link port and reads the last line — Passed or Failed — with no changes.

The design rule that makes it trustworthy: no check's expected value may be a number measured from an emulator. Every expectation is either computed a second, independent way on the machine itself, or is a documented hardware constant. Anything that cannot be settled that way is listed as untested, with its reason.

The eleven areas: the CPU's instruction results and flags; instruction and memory timing (CYC); the divider and timer; interrupts, including the HALT defect and EI's delay; the memory map; PPU display timing and bus blocking; the object-transfer DMA; the sound registers; MBC banking; the state the boot ROM handed over; and the link port itself.

The cartridge discriminates

Run on several implementations, the results spread out — which is the point. This is evidence that the cartridge tells machines apart, not a league table.

What it structurally cannot check

Being exact about the limit is what makes the rest worth trusting. A cartridge cannot see the picture — the PPU streams pixels to the panel and keeps none of them, so there is no framebuffer to read back; pixel accuracy is left to the Mealybug Tearoom tests and TerminalGB's own conformance tool. It cannot see anything finer than four dots, because the CPU only observes on machine-cycle boundaries, nor hear sound as sound — register behaviour is checked, what leaves the speaker is not. A double-speed bug that only changes which tile a single dot samples is purely a pixel, and no cartridge can read one; that failure mode is exactly what TerminalGB's pixel harness exists to catch instead.
