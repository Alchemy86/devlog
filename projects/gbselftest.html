The screen is 20 columns by 18 rows, so what fits there is the area verdicts and a list of codes. The link port carries the whole story. This is the failure from the Peanut-GB run above, verbatim, straight from the run that took the picture:

The -> lines are the point. Any suite can print FAIL. What an emulator author actually needs is a hypothesis about what behaviour is missing, in hardware terms they can act on, and somewhere to read about it. Every code is a stable anchor: codes are never reused and never renumbered, so one printed by a two-year-old build still means what it meant.

That is also why a failing run is more than twice as expensive as a passing one. The committed SameBoy DMG transcript is 8,423 bytes; the Peanut-GB one is 18,064. A Game Boy's link port runs at 8,192 bits per second, so the passing run spends about eight seconds shifting its report out and the failing one about eighteen. The explanations are the product, and they cost. A host that only wants the verdict can stop the moment it sees Passed or Failed — Blargg's convention, on purpose, so an existing test runner needs no changes at all.

The rule that makes the verdict worth anything

No check's expected value may be a number measured from an emulator.

GBSelfTest — the one rule

It sounds obvious and it is not, because the easy way to write a test cartridge is to run something on an emulator you trust, write down what it did, and assert that forever. That produces a suite which certifies agreement with one implementation and calls it accuracy.

Every expectation here is instead one of two things. Either it is computed a second, independent way on the machine itself:

  • the adder is checked against a counter built from INC HL, which sets no flags at all and goes through a different unit;
  • the logic operations are checked against De Morgan's law;
  • the rotates are checked by the fact that eight of them are the identity;
  • DAA is checked against decimal arithmetic done a digit at a time.

Or it is a documented constant that is a fact about the hardware — a register's read-back mask, an instruction's published cycle count, the 456 cycles in a scanline. A behaviour that can be checked neither way does not go in; it is listed as untested instead, with the reason, in the coverage statement the cartridge prints at the end of every run.

The second half of that rule is that the cartridge is validated against implementations nobody here wrote. It is developed against three at once, and a disagreement is investigated before anything ships. Two of the checks in this repository were wrong and were found that way — not by reasoning about them.

Catching a shortcut, not just a mistake

Most checks look for something an emulator got wrong. Two look for something it deliberately left out, and those are much harder, because a good shortcut is exactly one that keeps every total right.

An emulator that advances its peripherals once per instruction — or lets the processor run a batch of instructions and advances everything afterwards — still runs every clock at the correct rate. The frame is still 70,224 cycles. The timer still ticks at the documented rate. The interrupt is still delivered exactly once. Nothing measured over a run of instructions can see the difference, which is why the existing suites do not catch it and why emulators that do it can say so in their own documentation without ever failing anything.

What gives it away is an observation that depends on phase inside an instruction rather than on a rate:

CheckWhat it doesWhat a batched machine reports
GB-CYC-07 Reads one register twice from the same starting phase, once with a three-cycle instruction and once with a four-cycle one. The reads land on different cycles of their own instructions, so over four one-cycle delays the longer instruction must overtake the shorter exactly once. Both reads see the instruction's start. It never overtakes.
GB-CYC-08 Lets the timer overflow inside a sled of NOPs and has the handler read the return address off the stack, which names the instruction the interrupt landed on. Entering the sled one cycle later must move that landing back by exactly one instruction, eight times over. Delivery happens at a batch boundary. The landing stops moving.

Neither needs a reference, a host, or a number measured from anything. They are the cartridge doing the one job no external suite can do for you: telling you what your speed cost.

Rendering leaves a trace, even though the picture does not

A cartridge cannot see the screen. The picture processor streams pixels to the panel and keeps none of them; there is no framebuffer to read back and no way to judge one from the inside. So on the face of it a self-test cartridge can say nothing about rendering at all.

Except that mode 3 lasts exactly as long as the fetcher takes, and the fetcher takes longer when there is more to draw — a fine scroll offset, an object on the line, the window starting. So the cartridge lays out a scene whose cost is documented and measures how long mode 3 actually took. That is a real test of rendering behaviour with no reference image anywhere in it, and in practice it is the most discriminating thing here: it is what separates a renderer that draws a whole line at once from one that models the fetcher.

The measurement is worth spelling out, because it solves a problem that looks fatal. The coincidence interrupt is armed on one scanline, and the handler runs a variable number of NOPs before reading STAT once; a binary search over that delay finds the exact machine cycle at which the mode changes. The delay from the interrupt to the first NOP is unknown — and does not matter, because every result is the difference between two such edges and the unknown cancels. The floor is four dots, because a machine cycle is four dots and the processor cannot look between them.

And where that technique stops

The STAT-sled measures durations. It has nothing to say about content. TerminalGB's double-speed write-commit bug — the one written up here — changes only which tile source the fetcher reads from at a given dot: not how long anything takes, not any readable register, nothing DMA or interrupt related. GB-PPU-07's double-speed half checks the general fact that bug depended on (the dot clock does not speed up with the CPU) but cannot and does not check the bug itself, and no rewording of a timing check ever will. When a picture bug's only effect is which of two already-equal-cost sources gets read, it needs Mealybug or a screenshot, not this cartridge. Being exact about the limit is what makes the rest of it worth trusting.

A hundred checks in one session is a shape no test ROM has

GB-DMA-06 found a real bug in TerminalGB on the day it was written, and the bug was invisible to every public suite that emulator gates on — thousands of rows across Gambatte, Mooneye, Mealybug, SameSuite and the c-sp aggregation were byte-identical either way.

The fault was a flag the picture processor kept about a running object transfer, cleared on one of the two paths that can notice the transfer has ended and not the other. Once it latched, the object scan never read object memory again for the rest of the run.

A suite of short ROMs cannot see that. Each one boots, measures one thing and stops, so a latch that needs a transfer to end on an instruction boundary and a scan to follow it never gets the chance. This cartridge runs a hundred checks back to back on one machine, and that is the shape that catches it.

The check itself is a nice piece of indirection, because a cartridge cannot see which objects the scan found. What it can see is how long mode 3 took, and ten objects on a line cost the fetcher at least sixty dots. So: leave object memory entirely empty, put the visible objects in the transfer's source, and start the transfer so it covers the measured line's scan. A machine whose scan reads object memory straight through the transfer finds the ten objects the transfer has already written and is still drawing them; hardware finds none and is already in horizontal blank.

Two details in that check are load-bearing rather than decorative. Object memory is left empty on purpose, so that whatever slot the scan last managed to read, it read a zero — the frozen Y puts the phantom object above the screen, and the check does not depend on where the freeze landed. And the transfer is sourced from video memory rather than work memory, because on a monochrome console work memory sits on the cartridge's own bus and a transfer out of it would feed the processor its own bytes instead of instructions. That is why every real game's transfer routine lives in high RAM.

The standing rule this produced: when a check is written, run the whole cartridge and read the total, not just that check's line. A new check that passes in isolation and moves an unrelated area's verdict has found something.

Three ways this cartridge has been wrong about itself

A project whose whole pitch is "measure it, do not assume it" collects a specific kind of failure: the assumption you did not notice you were making. All three of these shipped, and all three are written down beside the fix.

The run decided the verdict, not the machine

GB-CYC-07 shipped once in a form that zeroed the timer counter and then restarted the divider. Three cycles separate those two writes, and whether the tapped bit falls inside them depends on the counter phase the check was entered in — which is set by how much code ran above it. So the verdict was decided by which checks failed earlier rather than by the machine. It passed on one emulator and failed on SameBoy, and swapping the earlier failures swapped the answer.

The rule that came out of it: restart the counter first and zero the timer after it, and sweep more than one delay rather than sampling once. Anything that reads a timer edge and does not do both is measuring the rest of the run.

A subroutine that quietly ate the measurement

FlipSpeed runs the documented STOP-based speed-switch sequence and, like every subroutine in that file, makes no promise about which registers survive it — it loads A repeatedly on the way through. A check that measured something into A, then called FlipSpeed to return to the starting speed, then compared against A, was comparing FlipSpeed's own leftover value.

The dangerous part is that it does so silently, producing a plausible and constant wrong number rather than a crash. It shipped in GB-PPU-07's double-speed half and was only caught because the wrong number ($1) disagreed with an independent measurement on two unrelated emulators that had already established the right one ($2). Save into a register FlipSpeed does not touch.

Two checks that skipped on every console, forever

This is the best of the three, because nothing about it looks wrong. The build did not pass rgbfix -c, so the ROM's header byte at $0143 was $00 — and a real Color console boots a cartridge with no Color flag into DMG compatibility mode, where KEY1 and double speed do not exist at all.

Meanwhile the cartridge's own console detection still correctly reported CGB, because it reads the boot handover registers, which do not care about the cartridge's header. So a double-speed check written the ordinary way built, linked, and skipped on every run, on every console, forever — and nothing looked wrong until somebody specifically asked whether it had ever run. Confirmed by building both ways and watching GB-CYC-09 and GB-PPU-07 go from permanently-skip to actually-run with zero change to any other check's verdict on any console.

Which is why a skip is counted separately

A skip is not a pass, and it is not a failure either. Each one prints its own reason in the run, so a skipped row is never silent — and two of the 102 do not judge at all: they report, printing the number they saw and leaving the verdict to a reader who has real hardware, because no published reference settles what the right answer is.

A suite everybody passes measures nothing, and the spread here is the property this project exists to have. Every implementation in that table is doing what it set out to do. TerminalGB's two rows are one emulator with two renderers behind it, and the eight-row gap between them is the fetcher model alone. Peanut-GB is built to run a Game Boy on a microcontroller and renders line by line. The rows are not a ranking; they are the range the checks can tell apart.

One caveat is carried in the repository rather than hidden: the TerminalGB rows are measured against a pinned revision that is old enough to predate a fair amount of accuracy work on the other side — including the object-DMA bus-sharing model GB-DMA-06 itself prompted. So those rows will keep scoring below checks a current TerminalGB build passes outright. That is the pin, not a finding, and re-pinning is a deliberate action that moves every row in the table at once.

A check earns its place by being all four of these

  1. Self-verifying. Its expected value is computed on the machine or is a documented hardware constant. If you had to measure it on an emulator to find out what it should be, it does not go in.
  2. Discriminating. A careful implementation and a rough one give different answers. Something everything passes is a check that measures nothing.
  3. Explained. One line saying what behaviour is missing, in hardware terms an author can act on. A check that only says FAIL is half a check.
  4. Bounded. It cannot hang. Anything that waits for an event waits with a limit; anything that waits for an event a broken machine might never deliver checks first that the machine can deliver it, and skips if not.

Everything the documentation shows is regenerated rather than edited — the check reference is written from the registry the ROM is built from, the screenshots are re-taken from the emulators' own framebuffers, the scoreboard re-runs every row — and CI is red if any of it has drifted. If a number in the README changes, it is because a run said so.

Where these numbers come from

The scoreboard was measured on 24 Aug 2026 by tools/scoreboard.sh, which runs every row and writes docs/scoreboard.md, naming the exact revision of each emulator: SameBoy 213a12c, TerminalGB 2467c65, Peanut-GB 8e65698, with the cartridge built from the RGBDS version pinned in tools/fetch-rgbds.sh. Nothing is vendored — each runner fetches, pins and builds its own emulator.

Both screenshots and the failure excerpt are committed artefacts of real runs, regenerated by tools/screenshots.sh; the byte counts (8,423 and 18,064) are read off the committed transcripts' own cost lines. The eight- and eighteen-second serial figures are those byte counts divided by the Game Boy link port's 8,192 bits per second.

The cartridge contains no third-party source, no boot-ROM extract and no game data of any kind: the font is drawn for it, the register definitions are written out from the public-domain Pan Docs, and the whole thing is MIT so anybody can take it, ship it and change it.
